# 新入社員オンボーディング手順

新しく参加した人が、初日から1ヶ月で何をすればいいかをまとめたガイドです。受け入れ側のメンターが本手順に沿って支援します。

## 期間別マイルストーン

| 期間 | ゴール | 主な活動 |
| --- | --- | --- |
| 1日目 | 全体像をつかむ | 環境セットアップ・ドキュメント通読 |
| 1週目 | 小さく動かす | 既存コードを追う・worktree→PRを1回経験 |
| 1ヶ月目 | 機能実装に貢献 | backlogタスク担当・リリース駆動フロー完遂 |

## 1日目: 全体像をつかむ

### セットアップ

1. リポジトリを clone して依存をインストール（ルートの README.md の手順通り）
2. Docker Compose を起動 → [http://localhost:3002](http://localhost:3002) でフロントエンドが見えれば OK
3. `php artisan test` で全テストが通ることを確認
4. `npm run secrets:bootstrap` で age 鍵生成と Keychain 登録、`secrets/*.enc.yaml` の復号セットアップ（詳細は handbook/policy/secrets-management.md）

### 読むもの（上から順に）

1. handbook/README.md（handbook ディレクトリの使い方）
2. handbook/architecture/overview.md（Lexis の全体像と守るべき約束ごと）
3. .ai/vdd/VISION.md（プロダクトのビジョン）
4. CLAUDE.md（開発ルール、特に worktree とリリース駆動の章）
5. process/RDD.md（リリース駆動開発の方法論）

### 1日目終わりに答えられるべきこと

- Lexis は何をするプロダクトか？
- バックエンド・フロントエンド・DB はそれぞれ何を使っているか？
- 「Working Tree」「Commit」「Tree」「Blob」「Materialized View」の違いを1行で
- 自分が興味ある領域の担当者は誰か？

## 1週目: 小さく動かす

1. `.ai/release-specs/` から1つ選び、過去にどういう実装がされたかを読みながら該当コードを追う
2. ローカルで動作させて、フロントエンドから手動操作してバックエンドのログを観察する
3. 小さな変更（タイポ修正・コメント追加）から始めて、worktree → release branch → PR の流れを1回経験する（手順: .ai/WORKFLOW.md）

### 1週目終わりに答えられるべきこと

- worktree を作って release branch で作業し、develop に PR を出す手順
- 触ったコードがどの領域に属するか、担当者は誰か

## 1ヶ月目: 機能実装に貢献する

1. `backlog/items/` から優先度 P2 以下のタスクを1つ選んで担当する
2. リリース駆動のフロー（要件定義 → 設計対話 → TDD 実装 → セルフチェック → PR）を完遂する
3. 自分のレビュー対象 PR で、handbook の更新が漏れていないかも見る習慣をつける

### 1ヶ月目終わりに答えられるべきこと

- 自分が担当を引き継げる領域はどれか？
- ハンドブックのどの部分が薄くて困ったか？

## 役割別のリソース

| 役割 | 主なリソース |
| --- | --- |
| Frontend | CLAUDE.md のフロントエンド規約 / aspida + SWR + Zod + react-hook-form のパターン（既存 frontend/src/hooks/）/ shadcn/ui 利用ルール |
| Backend | レイヤー構造（Controller → UseCase → Service → Model）の厳守 / TDD 必須（テストを先に書く）/ マイグレーションを伴う変更は担当者に確認 |
| Infra・Deploy | DEPLOYMENT.md / infra/ 配下の Terraform / .github/workflows/ の GitHub Actions |
